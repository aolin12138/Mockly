Thinking & Logic

Your chosen approach was the brute-force baseline: for each index i, scan all later indices j to check whether nums[i] + nums[j] equals target. That logic is correct for finding a valid pair and prevents reusing the same element by enforcing j > i. However, the reasoning broke down in complexity analysis: a nested scan over remaining elements per i results in quadratic total work, which violates the explicit performance requirement for large inputs.

Code Assessment

The final code matches the answer key’s brute-force solution (nested loops), which is correct on many cases but has O(n^2) time and is not acceptable under the stated constraints—this is consistent with passing 9/10 tests and failing a hidden performance case. The canonical optimal solution is a single pass with a hash map of seen values to indices: for each num, compute complement = target - num, check if complement is already in the map, and if so return the stored index and current index; otherwise store num -> i. That achieves O(n) time and will pass the largest hidden test that your current approach likely times out on.
