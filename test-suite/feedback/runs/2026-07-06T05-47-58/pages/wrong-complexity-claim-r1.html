Thinking & Logic

Your approach was the classic brute-force: for each index i, scan subsequent indices j to find a pair summing to target. That logic is correct for functional correctness, but it performs O(n^2) pair checks in the worst case. Despite passing visible tests, the hidden failure is consistent with hitting a time limit at the upper constraint (n=1e5), where O(n^2) is infeasible.

Code Assessment

Compared to the canonical optimal solution, your code uses the brute-force nested-loop pattern and misses the key optimization: a hash map from value → index to find the complement in O(1) average time per element. The optimal technique achieves O(n) time by checking whether (target - nums[i]) has been seen before inserting nums[i]. Your solution also claimed O(n) complexity, but the nested loops are definitively O(n^2), which is exactly the pitfall called out in the answer key.
