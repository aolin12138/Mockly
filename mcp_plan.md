# Plan 2 — The MCP Server (Node/TypeScript backend) + Interview Tools

**Goal:** Stand up a central MCP server, hosted by your own backend, that all provisioned ElevenLabs agents connect to. It exposes the tools the interview agent calls mid-conversation. It holds **data + execution** logic, never hint logic (hints are generated by the agent itself).

**Stack:** Node/TypeScript. Code execution via **Judge0** (already in use).

---

## 1. What to build the server with

Use the **official MCP TypeScript SDK** (`@modelcontextprotocol/sdk`). It provides a `McpServer` you register tools on, plus transport adapters.

**Transport: HTTP-streamable.** ElevenLabs supports both SSE and HTTP-streamable remote MCP servers. HTTP-streamable is the current standard and the right default. The SDK's `StreamableHTTPServerTransport` mounts as an HTTP handler.

**Hosting model — two options:**

- **(A) Mount inside your existing backend.** Add an MCP route (e.g. `POST /mcp`) to your existing Node app, reusing your DB connections, your question store, and your Judge0 client directly. *Recommended* — least moving parts, and the tools need your DB/Judge0 anyway.
- **(B) Standalone MCP microservice.** Separate process/deploy. Only worth it if you want independent scaling or isolation. Adds inter-service calls to reach your DB/Judge0.

Go with (A) unless you have a specific reason not to.

---

## 2. How the agent connects to this server (the wiring)

From Plan 1, the agent is created (on the user's EL account) with this MCP server attached as a tool source. At conversation time:

1. EL agent decides to call a tool (e.g. fetch code).
2. EL sends an MCP request to your server URL over HTTP-streamable.
3. Your server authenticates the request, runs the tool, returns a result.
4. The agent uses the result in its next turn.

**Identifying the session — the critical piece.** Your MCP server must know *which interview* a tool call belongs to (whose code to fetch, which question's tests to run). Mechanism:

- At conversation start (Plan 2 / start-interview endpoint) you pass a `secret__session_id` dynamic variable. Secret dynamic variables are sent only in dynamic-variable **headers** and never to the LLM — ideal for a session/auth id.
- Configure the agent's MCP tool so this secret rides as an HTTP **header** (e.g. `X-Session-Id`, or a bearer token encoding the session) on every MCP request.
- Your MCP server reads that header, looks up the session (user, question id, start time, language), and scopes the tool to it.

**Auth between EL and your server:** require a shared secret header (server-to-server) in addition to the session id, so only ElevenLabs-originated calls are honored. Optionally IP-allowlist EL's static egress IPs. All over HTTPS.

## 3. Session state the server needs

Before tools can work, the start-interview endpoint must record a session row your MCP tools read:

```
interview_session {
  session_id        // matches secret__session_id
  user_id
  question_id
  language_id       // Judge0 language id
  started_at        // for elapsed/remaining time
  time_budget_secs
  hint_count        // updated as hints are given (optional)
  status
}
```

The "current code" itself lives wherever your textarea autosaves it — either you push code to the backend continuously (preferred: the server always has latest), or the MCP tool pulls it from a `latest_code[session_id]` store. Decide this; the tools below assume the server can read the latest code for a session.

## 4. The tools

You named two. Here's the recommended set, with the important design point: **two code-fetch variants differ by whether they run tests AND by how much they reveal.**

### Tool 1 — `get_current_code` (no test run)
**Purpose:** Let the agent see what the candidate is currently writing, cheaply, without execution. Used for the "understand what they're doing / are they stuck" judgment during Implementation.

**Input:** none (session resolved from header) — or optional `reason`.
**Does:** reads latest code + language for the session; returns it plus session metadata.
**Returns (compact JSON):**
```json
{
  "code": "<candidate's current source>",
  "language": "python",
  "elapsed_seconds": 612,
  "remaining_seconds": 588,
  "phase_hint": "implementation",
  "hint_count": 2
}
```
The `elapsed/remaining_seconds` here is what feeds the **Implementation→Closing** workflow edge: map it into a dynamic variable via the tool's response assignment (dot-path), and the edge condition reads it. This is your clock-sync — no separate timer needed.

**No execution → fast.** This is the one the agent can call often.

### Tool 2 — `run_code_against_tests` (executes via Judge0, LOSSY summary)
**Purpose:** Tell the agent whether the candidate's current code is actually working, **without leaking hidden test cases.** This is the "fetch codes with test cases" tool — but note it returns a *signal*, not the raw failing inputs.

**Input:** none (session resolved from header) — optionally `subset: boolean` to run a reduced set during live sessions for latency.
**Does:**
1. Reads latest code + `language_id` for the session.
2. Loads the question's hidden `test_cases` from your DB.
3. Submits to Judge0 (see §5).
4. **Summarizes lossily** before returning.

**Returns (deliberately non-leaking):**
```json
{
  "passed": 7,
  "total": 10,
  "all_passed": false,
  "failure_category": "edge_case",   // e.g. basic_case | edge_case | timeout | runtime_error | compile_error
  "elapsed_seconds": 612,
  "remaining_seconds": 588

  
}
```
**Hard rule:** never return the failing input, the expected output, or the actual output to the *live* agent. Surfacing a hidden case through the agent leaks part of the problem. The agent gets enough to decide *whether and how hard to hint* — the failure *category* (e.g. "fails on an edge case", "times out on large inputs") is the maximum granularity. Map the category to your DB's `common_pitfalls` so the agent's hint can be relevant without being a giveaway.

### Tool 3 — `log_event` (recommended, optional for v1)
**Purpose:** Record hints given, phase transitions, code snapshots, for the **post-session feedback agent** to consume from one schema.
**Input:** `event_type` (`hint_given` | `phase_change` | `code_snapshot` | ...), `payload`.
**Does:** appends to an events table keyed by `session_id`. Also bump `hint_count` on `hint_given`.

### NOT a tool: the final feedback run
The fully-detailed post-session run (full test set, real pass/fail with inputs/outputs) is **not** an agent tool — the agent never sees it. It's triggered by your backend on session end and handed to the feedback agent. Use the **same Judge0 execution code** as Tool 2 but the **detailed (non-lossy) summary shape**. One runner, two summary shapes.

## 5. Judge0 integration details (verified API shape)

- **Endpoint:** `POST {JUDGE0}/submissions` to create; `GET {JUDGE0}/submissions/{token}` to poll. Use `?wait=true` to get the result inline on create (note: `wait=true` "may or may not be enabled on all Judge0 hosts" — confirm on yours; if disabled, poll the token).
- **Base64:** if source/stdin/expected_output may contain characters that don't serialize cleanly to JSON, set `?base64_encoded=true` and base64-encode `source_code`, `stdin`, and `expected_output`. Safer to always base64 for arbitrary candidate code.
- **Per-test fields:** each submission takes `source_code`, `language_id`, `stdin`, `expected_output`. Judge0 compares output to `expected_output` and returns a `status` (e.g. Accepted / Wrong Answer / Time Limit Exceeded / Runtime Error / Compilation Error). Map these statuses → your `failure_category`.
- **Limits:** set `cpu_time_limit`, `wall_time_limit`, `memory_limit` per submission so "timeout" is a real, bounded signal.
- **Multiple test cases:** use Judge0's **batch submissions** (`POST {JUDGE0}/submissions/batch`) to run all of a question's test cases in one round-trip instead of N sequential calls — important for keeping live `run_code_against_tests` latency low. Collect the batch tokens, then fetch results.
- **Status → category mapping (build this):**
  - Compilation Error → `compile_error`
  - Runtime Error (NZEC etc.) → `runtime_error`
  - Time Limit Exceeded → `timeout`
  - Wrong Answer on a basic/example case → `basic_case`
  - Wrong Answer only on edge cases → `edge_case`
  - All Accepted → `all_passed: true`

## 6. Latency considerations (this is a VOICE conversation)

- `get_current_code` is read-only → fast, call freely.
- `run_code_against_tests` invokes Judge0 → seconds. Mitigations: use **batch** submissions; consider a `subset` of tests during live runs (full set reserved for the post-session run); cache the last run if code is unchanged. The agent should be told (in its prompt) that running tests takes a moment so it can set expectations or keep talking.
- Avoid making the agent block silently on a long Judge0 run — keep live runs bounded.

## 7. Server skeleton (shape, not full code)

```
POST /mcp  (StreamableHTTPServerTransport)
  → auth middleware: verify shared secret header + resolve session from X-Session-Id
  → McpServer with registered tools:
       get_current_code
       run_code_against_tests
       log_event
  → each tool handler:
       resolves session row (user, question, language, started_at)
       does its work (DB read / Judge0 call)
       returns compact JSON (lossy where required)
```

Tools are registered with a name, a description (the agent reads this to decide when to call — write these carefully), and an input schema (zod). Keep descriptions behaviorally precise, e.g. for `run_code_against_tests`: "Check whether the candidate's current code passes the problem's tests. Returns pass counts and a failure category only — never the failing inputs."

## 9. Security recap

- HTTPS only.
- Shared-secret header for server-to-server auth; reject calls without it.
- Session id via **secret** dynamic variable → header, never to the LLM.
- Optionally IP-allowlist ElevenLabs' static egress IPs.
- `run_code_against_tests` must never return failing inputs/expected outputs to the live agent — enforce this in the tool, not just the prompt.
- Judge0: bound every submission with time/memory limits; treat candidate code as untrusted (Judge0's sandbox handles execution isolation, but still cap resources).
